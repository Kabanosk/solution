## Goal
`classify(action, context) -> PolicyDecision` per D-005, CEO overrides as `Rule`, `parse_rule(text, llm)`: `.house/tasks/T003-policy-engine.md`.

## What was done
New files only (`backend/cfo/agent/__init__.py`, `backend/cfo/agent/policy.py`, `backend/tests/test_policy.py`).
- `PolicyAction(action_type, amount|None, supplier, category)`, `PolicyContext(avg_monthly_inflows, typical_amounts, rules)`, `PolicyDecision(level, reason)`.
- `classify` is pure. Order, first hit wins: (1) newest matching active CEO rule; (2) strategic action types (`request_credit_line`, `open_deposit`, `make_investment`, `fx_hedge`, `change_team_budget`) -> APPROVAL at any amount; (3) no amount -> AUTO; (4) routine (known supplier, within +-20% of typical, bounds inclusive) -> AUTO regardless of amount; (5) < 1% of average monthly inflows -> AUTO, but NOTIFY for a new supplier; (6) > 5% or inflows unknown/zero -> APPROVAL; (7) new supplier -> APPROVAL; (8) rest (1%..5% inclusive, known supplier) -> NOTIFY. Amount sign ignored; supplier/category matching is case- and whitespace-insensitive. `reason` is one English sentence (CEO rule reasons quote the CEO's text).
- `context_from_transactions(txns, rules)`: typical = median absolute outflow per counterparty; avg monthly inflows = positive amounts over the calendar months the statement spans (None with no data).
- `parse_rule(text, llm, categories=())`: LLM tool call `create_rule(level, category?, supplier?, action_type?)`, falls back to a JSON object in the reply; normalises (level upper-case, category/action_type lower-case); raises `ValueError` for blank text, bad level, wrong tool or no match field.

## Rule matching fields (T001 proposal)
Kept `category`, `supplier`, `action_type` unchanged: no change to `domain.py` or `schema.sql`, so fully backward-compatible. Semantics fixed here: all non-empty fields must match (AND), a rule with no match field never matches, inactive rules ignored, newest `created_at` wins (later list position breaks ties). A possible later refinement (not done, would need a schema column) is an amount cap on a rule ("equipment under 200 EUR is fine").

## Interpretation choices worth a look
- D-005 is ambiguous on "new supplier" vs "< 1% of inflows"; the coordinator ruled: a new supplier is never AUTO. Below 1% it is NOTIFY (reason mentions the new supplier), otherwise APPROVAL. Routine payments (known supplier) stay AUTO regardless of amount.
- "Routine" beats the 5% limit (D-005: AUTO regardless of amount).
- Demo step 4 (cloud invoice +50%) needs no special action type: as a `pay_invoice` of a known supplier at +50% of typical and a few % of inflows it comes out NOTIFY (tested).
- Step 7 ("sprzęt zawsze zatwierdzam sam") = `parse_rule` -> `Rule(category="equipment", level=APPROVAL)`; persisting is the caller's `Repository.add_rule`.
- Action type strings other than the strategic five are free-form; the agent task should use `pay_invoice` for payments so the parse_rule prompt matches.
