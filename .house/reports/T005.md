## Goal
Agent that handles one `Event` at a time (demo steps 2-3, 5-6, plus the step 4 sub-agent): `.house/tasks/T005-agent-graph.md`.

## What was done
New package files under `backend/cfo/agent/` (plus deps `langgraph`, `langgraph-checkpoint-postgres`, `pypdf`):
- `ports.py`: `Notifier` Protocol `send_dm(employee_id, text, level, actions=()) -> str` and `ActionButton(action_id, label, value)`. T011 adapts the T008 notifier to it. I did not touch `cfo/channels/`.
- `tools.py`: `ToolBox.call(server, tool, **args)`. `InProcessToolBox` (tests / single process: calls the T004 tool objects, JSON round-trip) and `McpToolBox` (production: official `mcp` client, stdio params or streamable-HTTP URL, one short session per call, safe inside a running event loop). I chose the plain `mcp` client over `langchain-mcp-adapters`: the agent calls tools from deterministic code, not a tool-calling loop. `Gateway` = typed helpers over the ToolBox.
- `documents.py`: PDF (pypdf, crude fallback), `.eml` (body + PDF attachments), text -> plain text.
- `llm_tasks.py`: the only LLM uses: `extract_invoice` (tool `submit_invoice`, JSON fallback, validated in code), `alternative_queries` (only when the invoice-number search finds nothing), `explain` (facts computed by code, template fallback on error/empty). All through `cfo.llm`.
- `investigate.py`: investigation sub-agent (own LangGraph: gather -> detect -> explain) that the main graph runs on its own for METRIC events (D-005/D-006).
- `graph.py`: `Agent.handle(event) -> HandleResult`, `Agent.resume_approval(approval_id, approved, by)`, `build_agent(...)`, `postgres_checkpointer(url, schema)`.
  - Reconcile (BANK_TRANSACTION / INVOICE_DOCUMENT / REMINDER): search owner's folders by invoice number -> read -> LLM extracts lines -> code compares total to the payment -> `attach_invoice` + AUTO decision + DM telling Grażyna what was read (D-004); mismatch -> `request_clarification`; nothing -> `request_invoice` with Belegpflicht text. Escalation is derived from the Decision history: request -> remind (REMINDER event) -> escalate to next in HR chain not on vacation -> ... -> `escalation_exhausted` (DM to CEO). On vacation people are skipped (recorded in `skipped_on_vacation`). The owner always gets an access notice if the DM went to someone else. `HandleResult.next_reminder_hours` tells the caller (T011) to schedule a REMINDER.
  - Liquidity (METRIC `{signal: "liquidity_forecast", month, min_balance, requested_amount}`): `classify` -> APPROVAL -> `request_approval` node (pending Decision + ApprovalRequest + DM with approve/reject buttons whose `value` is the approval id) -> `await_approval` node (`interrupt`). Approve -> Decision executed with `executed_simulated=True`, actor = approver; reject -> REJECTED. A CEO rule can lower the level (tested).
  - Cost anomaly (any other METRIC): sub-agent detects cost-per-unit up >= 20% and cost growing >= 20 points faster than the metric, names the biggest cost line (`CostMetric.detail`, flat mapping or `{"lines": [...]}`), NOTIFY decision + DM to CEO and team owner, once per kind and month.
  - T008 notes applied: `resume_approval` raises `PermissionError` if `by` is not the approver, `KeyError` for unknown approvals, and is idempotent (a repeated call returns `already_resolved`, nothing runs twice); `handle`/`resume_approval` share one lock (handlers may run in worker threads).
- Decisions are written through the repository (not the `record_decision` tool): the tool cannot pre-assign ids, update a pending decision or create an `ApprovalRequest`. Policy context uses the repository too, because `list_transactions` is capped at 500 rows and thresholds need the whole statement.
