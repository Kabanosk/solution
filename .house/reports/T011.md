## Goal
One entrypoint `python -m cfo.run` (simulator -> agent -> notifier, forecast and cost-metric checks scheduled) and a
protected `backend/tests/test_golden_path.py` driving demo-flow steps 1-7 with FakeLLM and a fake channel
(`.house/tasks/T011-integration.md`).

## What was done
- `backend/tests/test_golden_path.py` (written first, 18 tests, one shared world in schema `t011_test`): real generated
  data (history seed + December replay through the real `Simulator` with a fake clock), real agent graph, MCP tool
  objects in-process, policy, forecast model, chat router and REST API (`TestClient`); fakes are only the LLM (reads
  the real PDF text) and the channel (`FakeChannel`, a `cfo.channels.base.Notifier` with `click` / `say`).
- `backend/cfo/run.py`:
  - `build_runtime(repo_factory, tools, llm, channel, ...) -> Runtime`: builds the agent, adapts the T008 channel to
    the T005 `Notifier` port (`AgentNotifier`: employee id -> `Employee`, `ActionButton` -> `Action`), registers the
    approval and chat handlers and calls `cfo.api.deps.set_agent`.
  - `Runtime.on_event`: simulator subscriber. Adds `transaction_id` to replay events (they carry the whole bank line
    in `payload.transaction`, the agent reads `payload.transaction_id`; without this nothing is reconciled).
  - Reminders: `HandleResult.next_reminder_hours` -> row in table `agent_reminders` (due in simulated time, created
    with `CREATE TABLE IF NOT EXISTS`, `schema.sql` untouched); `pump` turns due rows into REMINDER events.
  - Scheduled checks on the simulated clock: cost vs metric every 24 sim-hours (METRIC event -> investigation
    sub-agent, already deduplicated per pair and month), liquidity review every 744 sim-hours and once when the
    replay has finished (`review_liquidity` -> `proposal.to_event()` -> agent; not repeated when a decision of the
    same action type and month exists). Intervals: `COST_CHECK_HOURS`, `LIQUIDITY_CHECK_HOURS`, `REMINDER_AFTER_HOURS`.
  - `Worker.run(stop)`: starts the channel, ticks the simulator, pumps, stops the channel. A failing tick or check is
    logged and the loop goes on.
  - `main`: applies the schema, MCP over HTTP when the three `MCP_*_URL` are set (else in-process tools), Slack when
    both tokens are set (else `LogChannel`, DMs go to the log), Postgres checkpointer, SIGINT/SIGTERM stop. The clock
    is left as it is (paused on a fresh DB); `--start [--speed N]` resumes it.
  - `attach_api()` (`AGENT_IN_API=1`, called from the FastAPI lifespan in `cfo/api/app.py`): the API process builds
    the same runtime without the Slack socket, so dashboard Approve/Reject and `POST /v1/sim:step` reach an agent.
    Works across processes because approvals are in the Postgres checkpointer and reminders in a table.
- `backend/cfo/chat.py` (`ChatRouter`): CEO only. One LLM call chooses `create_rule` (validated by the existing
  `parse_rule`, stored with a `create_rule` decision, demo step 7) or `plan_purchase` (amount + month -> `Outflow` ->
  forecast; a gap -> credit line proposal handed to the agent, D-013 b). Other people get a refusal.
- `backend/cfo/agent/graph.py` (2 lines): the DM confirming an approved simulated execution is labelled `SIMULATED`
  instead of `APPROVAL` (demo-flow: "wykonanie oznaczone SIMULATED").
- Deploy: `worker.yaml` and `api.yaml` mount `cfo-data` read-only at `/app/data` (the replay file; `/v1/sim` in the
  api pod had no events file before), worker gets `FORECAST_MODEL_PATH`, api gets `AGENT_IN_API=1` and `cfo-secrets`;
  README section; `.env.example` lists the new variables.

## Differences from demo-flow.md and decisions (reported, behaviour not changed silently)
- **Step 5:** demo-flow says the forecast shows about -20k EUR in June and the agent proposes a credit line. Following
  D-013 the scheduled review proposes an **investment** (23,000 EUR) and the credit line only comes from the CEO's
  what-if. demo-flow.md step 5 should be rewritten to match D-013.
- **Numbers after December:** with December in the database the what-if "oven 30k in March" gives a 9,000 EUR line
  (T016 measured 7,000 EUR on data to 30 Nov); the base investment is 23,000 EUR (T016: 24,500 EUR).
- **Order of steps 2 and 3:** the data books FLV-42026 (29 Dec) before AS-69664 (30 Dec), so step 3 happens first.
- **Step 3 escalation is short:** Grazyna's manager is Vincenzo, so after one reminder to him the chain is exhausted
  ("Nobody could provide invoice ...") two simulated days after the payment. That is T005 behaviour; with the demo at
  3600x this DM arrives 48 s after the first one.
- **Step 4 timing:** the cloud alert fires on the METRIC event of 31 Dec 08:00; the liquidity proposal follows when
  the replay finishes (31 Dec 09:00), so the order 4 then 5 holds.

## Tested and did not work
- First run of the test: the agent ignored every replay event, because the events have no `transaction_id` (fixed by
  `normalize_event` in `cfo.run`, not in the graph or the data).
- Asserting the wording of the cost alert DM: the text is whatever the LLM returns from `explain`; the test asserts
  the code-computed facts in the decision payload and that the DM equals the decision summary.
- Full suite once failed in `test_agent.py::test_no_llm_query_wording_when_number_search_hits` (plus a teardown
  error) while other workers were running tests on the same Postgres: fixed schema name `t005_test` is shared between
  parallel runs. Not caused by this branch; same flake as in D-014.
