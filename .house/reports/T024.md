## Finding: managed MLflow in RHOAI (short web research, not verified on the cluster)
Yes, RHOAI ships a managed MLflow, but it is an operator-managed, cluster-scoped, one-per-cluster component, not something to count on in a shared namespace.
- Enabled in the DataScienceCluster by setting component `mlflowoperator` to `managementState: Managed` (default `Removed`), e.g. `oc patch datasciencecluster default-dsc --type merge -p '{"spec":{"components":{"mlflowoperator":{"managementState":"Managed"}}}}'`; check with `.status.installedComponents.mlflowoperator`. The MLflow resource is cluster scoped (only one instance), deployed by the operator in `redhat-ods-applications`; server version 3.10.1 in 3.4, SDK >= 3.11 advised. Technology Preview in 3.4 EA2; I could not confirm the GA/support status in 3.5 (3.5 docs return HTTP 403 to my fetcher; search snippets show 3.5 uses MLflow for the prompt registry and has a "Working with MLflow" guide). Also, "new components are not automatically added to an upgraded DataScienceCluster", so the `mlflowoperator` entry may be missing.
- Tracking URI: via the dashboard route, `https://<dashboard-host>/mlflow`, with `MLFLOW_TRACKING_AUTH=kubernetes-namespaced`, a bearer token (`oc whoami --show-token`) and `MLFLOW_WORKSPACE=<project name>`. Workbenches get the variables injected through the annotation `opendatahub.io/mlflow-instance`. Known issue RHOAIENG-44516: service-account tokens are not accepted through the dashboard URL; workaround is a Route straight to the MLflow service. So an in-cluster pod (our API/worker) would need token plumbing, which makes it a poor fit for a hackathon.
- Needs cluster-admin to patch the DSC, which this project does not have (single namespace).
- Sources: https://docs.redhat.com/en/documentation/red_hat_openshift_ai_self-managed/3.4/html/working_with_mlflow/installing-mlflow_mlflow , https://docs.redhat.com/en/documentation/red_hat_openshift_ai_self-managed/3.4/html/working_with_mlflow/installing-and-authenticating-mlflow-sdk_mlflow , https://docs.redhat.com/en/documentation/red_hat_openshift_ai_self-managed/3.4/html/working_with_mlflow/tracking-experiments-with-mlflow-in-workbenches , https://docs.redhat.com/en/documentation/red_hat_openshift_ai_self-managed/3.5/html/release_notes/index , https://rrbanda.github.io/rhoai-deploy-gitops/capabilities/mlflow , https://mlflow.org/docs/latest/self-hosting/security/network/

## What was done
Self-hosted fallback in `deploy/openshift/mlflow/` (own `kustomization.yaml`):
- `mlflow.yaml`: Deployment (`ghcr.io/mlflow/mlflow:v3.10.1`, tag verified to exist via the ghcr registry API; `strategy: Recreate`; requests 50m/256Mi, limits 500m/1Gi; `/health` probes), Service `mlflow:5000`, edge-TLS Route `mlflow` (http->https redirect). Command `mlflow server --host=0.0.0.0 --port=5000 --backend-store-uri=sqlite:////mlflow/mlflow.db --artifacts-destination=/mlflow/artifacts --serve-artifacts --allowed-hosts=... --cors-allowed-origins=*`. `HOME=/tmp` for the random OpenShift UID.
- `pvc.yaml`: `mlflow-data` 2Gi RWO (SQLite and artifacts). SQLite chosen over the existing Postgres: no `createdb` step, and the official image does not bundle a Postgres driver.
- `--allowed-hosts`: service names (with and without `:5000`, short and `.svc`/`.svc.cluster.local`), the default Route host pattern `mlflow-cfo-agent-uwur.*`, localhost. A custom Route host must be added.
- `README.md` in that folder.
- `deploy/kustomization.yaml`: only `openshift/mlflow` appended to `resources`. `deploy/openshift/app/configmap.yaml`: `MLFLOW_TRACKING_URI: "http://mlflow:5000"` plus a one-line comment.
