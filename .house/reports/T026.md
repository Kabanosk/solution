## Goal
The forecast model travels through MLflow: training registers it, the API serves the promoted version
(`tasks/T026-forecast-mlflow-registry.md`; D-009, D-015).

## What was done
- `backend/cfo/forecast/model.py`
  - `log_to_mlflow_if_configured(model, *, register=False, model_name="liquidity-forecast", alias="champion") -> str | None`:
    returns the run id (None when nothing was logged; it used to return a bool). Logs params, metrics, the booster
    (`name="model"`, pinned `xgboost==<version>` requirement, which skips MLflow's slow requirement inference),
    `feature_importances.json` and the sidecar as run artifact `forecast_model.meta.json`. With `register=True`
    it registers a new version and moves the alias to it. Sets `model.mlflow_run_id` / `model.model_version`.
  - `train(..., register=False)` passes the flag through.
  - `ForecastModel.load_from_mlflow(uri)`: accepts `models:/<name>@<alias>`, `models:/<name>/<version>` and
    `runs:/<run id>/model`. Rebuilds the `XGBRegressor` from the booster plus the sidecar and sets
    `mlflow_run_id`, `model_version`, `trained_at` (run start time). Raises on any problem.
  - `resolve_mlflow_model(uri) -> MlflowModelRef(uri, run_id, version)`: one cheap registry call, URI pinned to
    the version. `ForecastModel.meta()` / `from_meta()` are shared by the file and the MLflow path.
  - Experiment name: `MLFLOW_EXPERIMENT_NAME` if set, else `liquidity-forecast`.
  - Auth: nothing is hardcoded. The code only calls `mlflow.set_tracking_uri($MLFLOW_TRACKING_URI)`; token,
    workspace and TLS come from MLflow's own variables, so `MLFLOW_TRACKING_AUTH=kubernetes-namespaced` works
    unchanged on the client side.
- `backend/cfo/config.py`: `forecast_model_uri` (`FORECAST_MODEL_URI`, default empty).
- `backend/cfo/api/services.py::forecast_model`: when `FORECAST_MODEL_URI` and `MLFLOW_TRACKING_URI` are both set
  it serves the registry model. The alias is resolved at most every 60 s and the model is downloaded only when
  the run or version changed. The MLflow call runs on a daemon thread with a 20 s limit, because the MLflow HTTP
  client retries for minutes when the server is down. Any error or timeout is a warning and is remembered for
  60 s. `ForecastModelInfo.version` is the registry version (`"1"`, ...) and `mlflow_run_id` is filled;
  the local model keeps `trained-until-<date>` and `null`. `reset_forecast_cache()` added for tests.
- `backend/pyproject.toml`: extra `mlflow = ["mlflow>=3"]` (one line), `uv.lock` regenerated (resolves 3.18.0).
- `INFRA.md` §5 and `.env.example`: `FORECAST_MODEL_URI`, plus the standard `MLFLOW_*` client variables.
- `backend/tests/test_forecast_registry.py` (11 tests, real mlflow, temp sqlite store and artifact dir, no server,
  no Postgres; skipped without the extra). `tests/test_forecast_model.py`: the fake mlflow module was adapted to
  the new calls (`log_model(name=...)`, run object with `info.run_id`) and asserts the sidecar artifact.

## Deviations from the task text
- **MLflow fails after a version was already loaded: the API keeps serving that version** instead of switching
  to the local file. Falling back to a locally trained model would change the forecast on the dashboard on every
  MLflow blip. Before any version was loaded, the fallback is the file / train-on-first-use path as specified.
- When the registry was asked and gave nothing, the train-on-first-use fallback does not log to MLflow (it would
  wait for the dead server a second time). Without `FORECAST_MODEL_URI` the first-use training logs as before.
- `MLFLOW_TRACKING_URI` is read from the process environment only (as in T015), not from `.env`;
  `FORECAST_MODEL_URI` is a normal setting and works from both.

## Not verified
- Nothing was run against a real server: neither the T024 Deployment (server v3.10.1, client 3.18.0) nor the

- `runs:/<id>/model` and registry URIs are covered; `models:/<name>/latest`, stage URIs and `models:/m-<id>`
  go through `mlflow.models.get_model_info` and are untested.
