## What was done
- Item 9: `Repository.add_transaction` upserts without touching `documented` / `invoice_id` (new `keep` set in
  `_insert`). `add_invoice` also keeps an existing link when the re-added invoice carries none (seed/replay copies
  of December invoices have `transaction_id = None`), otherwise a reseed would unlink a reconciled payment.
- Item 10: `load.reset` also truncates `sim_state` (only if the table exists; the simulator creates it lazily).
- Item 25: `Repository.transaction()` (nestable, rolls back on error; all repo commits go through `_commit`).
  `load.seed` is one transaction, new `load.load(repo, dir, reset_first=)` does truncate + seed in one; the CLI uses it.
- Item 11: `attach_invoice` (MCP) runs in one transaction: `SELECT ... FOR UPDATE` on the payment row
  (`lock_transaction`), `pg_advisory_xact_lock` on the invoice number (`lock_invoice_number`, covers a number that has
  no row yet), documented/amount checks, then the write. A number linked to another payment is refused with
  `invoice_linked_to_other_transaction` (nothing is written; invoice and lines untouched). An unlinked database
  invoice (invoice first) is still adopted. In `repo.add_invoice`, moving an invoice to another payment un-documents
  the previous payment.
- P3: `generate` validates the source CSV (and the scenario assertions) before deleting anything, and removes only its
  own top-level paths (`OWN_PATHS`) when `scenario.json` marks an earlier run; other files in `--out` survive.
- Tests: `backend/tests/test_data_integrity.py` (per-process schema `t040_test_<pid>`), includes two threaded race tests
  (5 rounds each).
