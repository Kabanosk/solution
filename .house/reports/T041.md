## Decision (small, for the coordinator)
`DecisionStatus` has no FAILED value, and adding one changes the API enum (`cfo/api/schemas.py`, out of scope). So a refused approved action is `ESCALATED` (handed back to a human) plus `payload.failed`. The approval request itself becomes APPROVED (the CEO did answer), which keeps `resume_approval` idempotent. If the dashboard should show "failed" explicitly, add the enum value in a contract task.

## Tested and did not work
- First draft of the alert-approval test reused one `Event` object, so the old `pending` state of its LangGraph thread (same event id) leaked into the next run and asked again. Fixed in code (the `alert` node now always sets `pending`, `None` clears it) and in the tests (a fresh event each time). Real events have unique ids, so this only affected tests, but the explicit reset is cheaper than the next surprise.
- The first escalation-history test used `list_decisions()` (limit 100) to read the result and failed for that reason; it now queries by SQL.

## Limits / Next
- Several approval-level alerts in one metric run: only the first is asked, the others are asked on the next cost check (the dedupe skips decided months). Fine for the demo (one anomaly a month).
- `redeliver_approvals` runs on the next event; a quiet system with a failed DM only retries when something happens. Wiring it to the pump tick in `cfo/run.py` is a one-line follow-up for whoever owns run.py.
- With a model that omits the invoice number in `submit_invoice`, reconciliation now asks a human instead of attaching. Granite should copy the number (it is a required field).

## Review (Codex round, final)
