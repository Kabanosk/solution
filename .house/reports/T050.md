# T050: Scout access control for salaries and task logs

- **Agent / model:** coder / sonnet
- **Branch / commits:** task/T050-scout-access, commit 3cdcf6d (plus merge of origin/main with PR #27 `send_dm`, no conflicts)
- **Date:** 2026-11-21

## Goal
Deterministic controls in code (D-029): salary rows only for CEO / the person / their managers, office manager gets
one aggregate line; `task_log` / `scout_tasks` only own tasks unless CEO. Task: `.house/tasks/T050-guardrails-feasibility.md`.

## What was done
- `backend/scout/audit.py`: the one policy place. `is_salary_row` + SQL twin `salary_sql`, `payee_of` (employee id,
  else the single HR name found in counterparty, then reference; ambiguous or unknown = None), `reports_of`
  (manager chain), `can_see_salary(viewer, role, payee, reports)`, `filter_salary_rows` (DENY for staff, MASK + one
  `Payroll (N employees): X EUR` line for the office manager), `can_see_task`, and `Audit.salary_filter` /
  `Audit.check_task` which write the audit rows (`salary_filter` DENY/MASK per hidden row; `access_check` DENY on `task:<id>`).
- `backend/scout/loops/toolbox.py`:
  - `search_payments`: salary and other rows are fetched separately (salary part limited by period only, filtered
    afterwards), so a narrow search (name, amount) cannot pry a salary out and the aggregate is never narrowed
    to the person asked about. Without bank access, staff/managers still get only their own / reports' salary rows
    (`audit.check` untouched); otherwise `access_denied` as before.
  - `missing_invoices`: rows filtered defensively (salary rows normally have no invoice number).
  - `team_budgets` (had NO access check): spend excludes salary rows, then adds back only the ones the asker may see.
  - `cash_position`: already bank-gated (office manager / CEO only), totals only, no per-person rows: no change.
  - `cost_trends`: reads `cost_metrics` (food/ads/cloud), not bank rows: no change (test pins it).
  - `scout_tasks`: non-CEO limited to `requested_by` or `owner_id` = asker; one DENY audit row if other tasks matched.
  - `task_log`: non-CEO denied (audited) for other people's tasks; unknown id still `not_found`.
- `backend/scout/schema.sql`: `audit_log.decision` now allows `MASK` (drop/add constraint, idempotent for existing DBs).
- Dashboard: `MASK` accepted by the `AuditRow` type and shown as an amber badge on the Audit page.
- Tests: `backend/tests/scout/test_salary_access.py` (15), `test_task_log_access.py` (6), written first (red on import).

## Deviations (could not implement exactly)
- The aggregate line is shown only when at least 2 distinct people are hidden. A "payroll total" over one person is
  that person's pay (e.g. a narrow period, or after the office manager's own report is subtracted), so a lone hidden
  payee is dropped and audited as DENY instead of MASK.
- Residual: with a very short `days` window an aggregate can still cover only salaries paid on that day; by itself
  it never names anyone and needs >= 2 payees. Not closed further.
- Company wage tax / social security rows (reference "Payroll Wage Tax ...") are not a person's pay and stay visible.
- Staff path of `search_payments` still writes the usual bank DENY audit row only when it answers `access_denied`;
  rows of others are never fetched for staff, so they produce no per-row salary_filter audit rows.
- `cash_position` for the office manager includes payroll in the 30-day totals (an aggregate, allowed by the rule).

## Tested and did not work
- First draft returned `Payroll (1 employee): 2,350.00 EUR` when the office manager searched for one person: the
  aggregate identified Yusuf's pay. Fixed by fetching salary rows independent of the search filters and by the
  min-2 rule (tests `test_specific_search_cannot_pry_a_salary_out`).
- First insert of MASK audit rows failed on the `audit_log_decision_check` constraint: schema extended.

## Review round 1 (Codex, `reports/review-T050.md`)
Fixed (each with a test in `test_salary_access.py` / `test_task_log_access.py`):
1. BLOCKER adjacent `days` windows: the office manager's payroll totals are now one line per whole calendar month,
   `Payroll YYYY-MM (N employees): X EUR` (`payroll_summary` is a list). The salary rows are fetched from the first day
   of the month that contains the query's cutoff, so the cutoff can never split a month; the visible (own / reports)
   rows are still cut at the real date. A month with fewer than 2 hidden payees is dropped and audited as DENY.
   `missing_invoices` no longer returns any total (it has nothing to do with payroll). Test: sliding the cutoff over
   27/28 October gives the same single line every time.
2. BLOCKER `cash_position`: numbers unchanged (the office manager needs the real balance). When a non-exec asker
   gets totals whose 30-day outflows include salary rows, one `salary_filter` MASK audit row is written, policy
   `cash-position: payroll included in totals`. Rejected as a change of numbers: the total is a legitimate finance
   figure; the residual inference (balance and 30-day outflow minus the visible outflows leaves the sum of the
   hidden payroll of that 30-day window, i.e. a single salary only if the window holds exactly one hidden payment)
   is accepted because staff have no such access, payroll is paid for several people together, and the monthly
   buckets give the same level of detail anyway. Logged, audited, not closed.
3. MAJOR payee resolution: the payee must be the one employee on which `employee_id`, counterparty and reference
   all agree; any conflict or more than one name means unknown, i.e. someone else's pay.
4. MAJOR staff audit: staff and managers without bank access now go through the same filter on all salary rows, so
   every hidden row writes its `salary_filter` DENY row (no more SQL narrowing by name before the audit).
5. MAJOR `task_log` race: the task row, the steps and a second read of the task row use one connection; the policy is
   evaluated on the second read, so a task that changed hands in between is denied. Test simulates a reassignment
   right after the first check.
6. MINOR 500-row cap: removed. Salary rows are bounded by the period (at most 400 days), so no cap is needed and no
   matching or summed row can be dropped. Test with 520 bulk rows plus an older matching row.
Not changed: the `search_payments` salary-part of the SQL still ignores the search words by design (blocker 1 of
round 0); they apply to the rows that stay visible.
