## What was done
- `backend/scout/guardrails.py` (new): `HttpGuardrails` client (`Verdict(status, activated_rails, latency)`, bearer
  token, 5 s timeout, `GUARDRAILS_URL` empty = disabled), fail-open (logged, audit `guardrail_unavailable`), and the
  policy functions `screen_human` (strikes, 7-day window, compliance DM on the 3rd block, counter reset),
  `screen_tool` (withheld text, CEO DM once per outside item), `screen_document`, `screen_output`. Each check is a
  `guardrails.check` MLflow span (config_id, status, rails, latency).
- Strikes need no new table: they are `audit_log` rows (`guardrail_check`, DENY, policy `user-input`, requester,
  resource = the prompt); a `guardrail_escalation` row resets the counter. No schema migration.
- Hooks (small edits): `loops/chat.py` (`on_dm` human check before routing, tool results in `answer`, `_finish`
  bot-output with `screen=False` for the fixed blocked reply), `chat_api.py` (dashboard turn in and out),
  `loops/toolbox.py` (`send_dm` message goes through `bot-output`; blocked: not sent, the asker gets the rephrase
  text via `Toolbox.blocked_reply`), `loops/invoicing.py` (document text screened before `extract_invoice` in
  `_match`, KSeF line text; `hold_flagged` creates a `flagged` step, a `proposed` step and the CEO approval card
  through `liquidity._ask_approval`; `decide_flagged` files on Approve, leaves unfiled on Reject), `loops/liquidity.py`
  (`_after_answer` branches to `decide_flagged` for flagged invoices).
- Flagged invoices: the model never reads the flagged text, so nothing is extracted. Approving files the payment's own
  number and amount (or the full KSeF document, which needs no extraction) against the payment.
- MLflow: `traced_llm(get_llm())` in the worker and `build_context` (chat API), `init_tracing()` in `worker.build`
  (the API app already calls it), one trace `scout.<job kind>` per job in `Worker.run_one`.
- Demo: scenario `poisoned` (`demo_data.py`, AS-77666, Asimex, -1873.50), `seed.plant_demo_evidence` plants
  `mailbox/002-invoice-AS-77666.eml` whose PDF footer carries an injected instruction (`invoice_pdf(notes=...)`);
  dashboard demo panel button and API route allow-list updated.
- Deploy (superseded by review round 1, see below): `GUARDRAILS_URL` in ConfigMap `cfo-config`; optional `envFrom` Secret `guardrails` (`GUARDRAILS_TOKEN`) on api and
  worker; `COMPLIANCE_CONTACT` comes through Secret `slack` (already `envFrom`). `docs/guardrails.md` has only the
  "App wiring" section (T051 owns the rest). `test_deploy_manifests` extended.
- Merged origin/main (PR #27, `send_dm`) first, as the coordinator asked.

## Review round 1 (codex, reports/review-T052.md)
Fixed (each with a test in `backend/tests/scout/test_guardrails.py`, now 40 tests; full backend suite 522 passed):
- BLOCKER chat_api wiring: my earlier string replace silently matched nothing. `build_context` now builds `guard=from_settings(...)`
  and `traced_llm(get_llm())`; test `test_default_chat_context_has_guardrails_and_tracing` builds the default context.
- History: the dashboard sends every user turn of the client-supplied history plus the new one in ONE `/checks` request
  (assistant turns are not screened); any block blocks the request, one strike per request.
- Audit exposure and 500-char truncation: `audit_log.resource` never holds checked content any more (config id, length,
  sha1 prefix). Blocked human prompts are stored in full in the new table `guardrail_strikes` (no API reads it); the
  compliance DM is built from it (each prompt cut to 700 chars in the DM, said so in the text).
- Concurrency: record, count, report and reset run in one transaction under `pg_advisory_xact_lock(person)`; the alert has
  exactly the strikes it marks reported (a mutation test without the lock fails).
- Recipient / failed DM: `COMPLIANCE_CONTACT` = employee id, or a Slack user id used as it is (`SlackUI` now DMs raw `U...`/`W...` ids);
  empty = CEO only. A DM that returns None or raises resets nothing and audits `guardrail_escalation_failed`.
- Flagged invoice approve: the original document stays attached as task evidence (mail id / file path, name, flagged rails);
  the filing uses the payment's number and amount and is marked unverified in the `acted` step, the outcome and the audit row
  `file_flagged_invoice`. KSeF documents are filed with their own fields. Without a document reference the card would not be built (a reference is always set).
- External-alert dedup: Postgres table `guardrail_alerts`, keyed by the item (mail hash of from/subject/date, file path, chat
  message hash, tool+content hash as the last resort), no task id; marked only after the DM was delivered. When several items
  are in one tool result and it is flagged, each item is checked on its own so only the flagged ones are reported.
- Integration with T051 (coordinator's facts): https URL `https://scout-guardrails.cfo-agent-uwur.svc.cluster.local` in the ConfigMap;
  TLS verified with `GUARDRAILS_CA` (default service CA path, system CAs when the file is missing); roles `user`, `tool` (with `tool_call_id`),
  one `assistant`; token env `GUARDRAILS_TOKEN` from Secret `scout-guardrails-client` key `token` (optional) on api and worker (my `guardrails` Secret is gone);
  warm-up call (30 s) in a daemon thread at worker start, 5 s per check. Docs and `test_deploy_manifests` updated.

## Review round 2 (integrated)
All 7 findings fixed (46 tests in `test_guardrails.py`; full backend suite on the integrated branch 609 passed, 5 skipped; `house check` T050, T051, T052 GREEN):
1. 8000-char cap: texts are cut into 8000-char chunks overlapping by 300, each a separate message (`tool`/`user`/`assistant` by config) in one `/checks` call, up to 100 chunks; any blocked chunk blocks. Test puts the instruction at the start, across the first boundary, in the middle and at the very end.
2. Client-supplied assistant turns: `guardrails.screen_history` checks them with `tool-result` in one call; if blocked each turn is checked on its own and a flagged one becomes `[content withheld: flagged by guardrail]` before it reaches the model or the compaction call. Audited as BLOCK, no strike.
3. Pending flagged invoice: `on_reply` ignores any reply while the task has a pending approval (step note + audit `flagged_pending`); the owner's Approve/Reject still works.
4. Original document: the bytes are stored in the new table `flagged_documents`; the evidence carries `document_id` and `sha256`, and `GET /v1/documents/{id}` (new `scout/documents_api.py`, included in the app; I could not edit `scout/api.py` because the commit hook flags its existing `GOOGLE_TOKEN = "https:..."` line as a secret; write token, `attachment`, `nosniff`) returns them. Tested for the mail path; the Slack path uses the same code (`_match` hands `data` to `hold_flagged`).
5. Unreported flagged candidate: `_alert_flagged` sends the once-per-document suspicious-content DM (key = ref + sha256, table `guardrail_alerts`) for every flagged candidate not shown on a card, also when another candidate matched. Limit: `_match` stops at the first matching candidate, so a flagged document listed after the match is never read nor reported (nothing of it reaches the model).
6. Compliance DM: short message + the full prompts uploaded as `blocked-prompts-<person>.txt` through the notifier; if no file can be sent the prompts are inlined, shortened to 700 characters.
7. BLOCK: `audit_log` constraint now allows ALLOW/DENY/MASK/BLOCK (CREATE and ALTER), `AuditEntry` accepts them (it also lacked MASK), guardrail blocks are recorded as BLOCK, the dashboard type has BLOCK with the red badge and the "DENY / BLOCK only" filter. Dashboard edits are type/label only; node_modules is absent here, so no `tsc` run. `guardrail_escalation_failed` stays DENY.
